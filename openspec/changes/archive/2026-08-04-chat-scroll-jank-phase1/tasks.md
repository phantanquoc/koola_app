## 4. Stop full-map serialization on the scroll hot path (fix group 3)

- [x] 4.1 In `ChatApp/src/services/media/mediaIndexService.ts`, keep `touch()` updating `lastAccess` in the in-memory map synchronously so eviction ordering stays correct and current
  - `touch()` still does `entry.lastAccess = now; indexMap.set(mediaKey, entry);` inline before anything else. `evictIfNeeded` and `get` read the same map, so ordering is authoritative the instant `touch()` returns — persistence timing is now the only thing that changed.
- [x] 4.2 Move `touch()`'s persistence off the scroll-critical path — defer and coalesce it so a burst of touches costs at most one write, instead of a synchronous whole-snapshot `JSON.stringify` per touch
  - `touch()` now calls `scheduleLastAccessFlush()` instead of `persistMap()`. That sets a dirty flag and arms a single 2s `setTimeout`; later calls return early while a flush is pending (timer OR queued interaction), so any burst collapses to one write. The timer then defers through `InteractionManager.runAfterInteractions` so the snapshot cannot land inside a scroll frame. Root cause note: the pre-existing per-key 5s debounce did *not* bound this — the first touch of each distinct key always passed the gate, so scrolling past N cached images cost N full serializations. The new window bounds it by wall-clock time; the per-key debounce is kept on top so a hot key can't keep re-arming the timer.
  - **Post-verification correction (MEDIUM 1).** This note and the code originally claimed an inline-write fallback was needed "where `InteractionManager` is unavailable (Node test env)". That premise was false: probing the actual jest environment returns `IM present: true, runAfterInteractions: function`, with a working `cancel` handle, because the `react-native` jest preset provides it and `InteractionManager` is pure JS (a `TaskQueue` drained via `setImmediate`) with no native-module dependency. No reachable environment lacks it — the three specs that mock `react-native` wholesale all supply `InteractionManager` themselves, and none of them load `mediaIndexService`. The guard was therefore unreachable dead code whose comment also implied the tests exercised the inline path when they in fact exercise the deferred one. The branch has been **removed** (not reworded) and the comment now states the accurate reason no fallback is needed.
- [x] 4.3 Keep structural writes (`set`, `deleteEntry`) persisting promptly — they carry the file paths that `media-cache-persistence` requires to survive a process restart
  - Both now call `persistNow()`, which writes synchronously and additionally absorbs any pending deferred flush (the snapshot already contains every current `lastAccess`, so nothing is lost and no redundant second write fires). `clearAll()` cancels the pending flush and clears the dirty flag so a queued snapshot cannot rewrite the storage key it just cleared.
- [x] 4.4 Leave the public API and the on-disk format unchanged so `load()`, `iterate()`, and every app-wide caller (Moments, avatars) keep working untouched
  - Exports are byte-identical in name, signature, and return type (`CACHE_ROOT_DIR`, `CACHE_CAP_BYTES`, `load`, `get`, `set`, `deleteEntry`, `touch`, `iterate`, `evictIfNeeded`, `clearAll`, `getCapBytes`, `setCapBytes`, `getTotalCachedBytes`). Storage is still the single `'entries'` JSON blob written by the same `persistMap()` body under MMKV id `'media-index'`, so `load()` needs no change and no migration exists. The three new helpers are module-private.
- [x] 4.5 Verify the LRU eviction contract still holds: `evictIfNeeded` reads `lastAccess` and must still evict least-recently-used entries first ← (verify: eviction ordering unchanged; index still rehydrates correctly after restart; no Moments/avatar regression)
